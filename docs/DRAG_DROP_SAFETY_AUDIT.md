# D4: reverse drag-and-drop safety audit (incomplete)

Audit date: 2026-10-30. Base: D3 `d8358e6c044901ae2977f3790152406f0043e886` (draft PR #6). This is a static, partial audit, not a release certification. D4 includes partial staging and cancellation changes; the remaining requirements below are not complete and the Windows changes are not verified on Windows. D1–D3 themselves remain unverified with Explorer and a real SFTP server. Do not merge on the strength of this document.

## Findings and residual risks

1. **TOCTOU / untrusted server:** `EnsureDirectoryComponents` and `GuardedSftpDownload` perform separate path checks and `OpenRead`. Replacement between checks and open, including a temporary symlink restored before subsequent checks, can escape the selected tree or select different content. Matching attributes and FSTAT size do not establish identity or immutable contents. Public SSH.NET API as investigated in D3 does not provide an atomic no-follow open of each path component or a verified full handle identity. Treat remote hosts and concurrently writable trees as untrusted for this guarantee; no safe guarantee is claimed. D3's checks reduce detectable cases, not the race. Server-side isolation or a protocol/implementation with suitable handle-relative no-follow semantics must be evaluated before claiming a fix.
2. **Sensitive staging:** `ShellStagingDirectory` now uses an exclusive Win32 directory creation with an explicit protected ACL and rejects volumes without persistent ACL support. This has been cross-compiled but not run or verified on Windows; access by administrators, SYSTEM, the same user, or parties with suitable parent-directory rights is not excluded. Parent-path/reparse substitution is not completely addressed. Cleanup is best effort. Crash, failure to delete, or retained COM references may leave sensitive data. No stale cleanup exists. A safe cleanup design must avoid deleting active sessions and defend against reparse-point substitution; blindly deleting old directories is unsafe. Executability is not prevented by this code. These are unresolved security requirements.
3. **Cancellation / liveness:** `GetData` passes `CancellationToken.None` to the cache and synchronously waits. Cache disposal now also unblocks waiters independently of whether the download cooperates. The view requests cancellation of tracked transfers on tab disposal or SFTP disconnection. Cleanup still waits for `EndOperation` when async extraction has begun. If a consumer fails to end the operation, the retained COM reference and cache may survive indefinitely. A stalled synchronous read observes cancellation only around calls; the configured SFTP exchange timeout is 15 minutes, not a bound on the whole operation. Explorer cancel, Escape, tab/app close, and forced disconnect are not proven to stop every operation. A timeout must not free an object while a consumer still owns it.
4. **Final destination and partial batches:** the temporary-file commit applies only to Teleclav's staging, not the destination written by Explorer. Explorer may create or overwrite files, leave partial files, or complete part of a tree. This code cannot certify an atomic batch or independently confirm that every destination file is durable and correct. Failure of an item must not be interpreted as full success; actual Explorer behavior and reporting are untested.
5. **Privacy:** `LoggingRemoteBrowser.DownloadFileWithinLimitAsync` records remote and local paths, sizes and operation status when session logging is enabled. Paths may themselves be sensitive. The inspected transfer method does not log contents or credentials, but this is not a complete privacy or telemetry audit. `ShowOperationWarning(ex.Message)` displays exception text; whether all possible server-provided errors are sanitized is unverified. Rollback logs the temporary path and exception.
6. **Lifetime and memory:** lease cleanup is synchronized and idempotent in the examined paths, but finalizer timing is nondeterministic; `ShellReadStream`'s disposal flag is not synchronized. Whether concurrent COM calls or disposal cause races is unverified. No real repeated-drag stress or process memory measurement was run.
7. **Change during read:** different size/visible attributes are rejected when observed. Same-size changes with preserved or restored timestamps, and changes after a check, may pass; there is no snapshot or verified source hash. A successful staged read is not proof of the originally planned state.

## Tests, fixes, and release blockers

A request already cancelled before `ShellDownloadCache.OpenAsync` acquired the lock previously reserved quota and queued a download. It now observes cancellation under the lock before creating an entry. A deterministic quota regression test, a 100-cycle cache cleanup test, a disposal cancellation test, registry race tests and a Windows ACL test were added; a standalone harness built with the same source failed on the baseline and passed after the fix, then passed 100 cache cleanup cycles. This is not a COM or Explorer stress test and does not measure process memory. The cache lifetime token now unblocks `GetData` on disposal; the view requests disposal on close or disconnection. Explorer cancellation itself and forced shutdown remain unverified. The Windows xUnit test cannot execute here. SDK 10.0.103 ran on Linux; the installer reported ownership errors. NuGet was restored with a Linux-compatible package path and static graph evaluation. The initial apparent no-output test success was not a test execution, because the Windows-style package path prevented the test SDK import. Windows-targeted application and test projects built on Linux with zero errors or warnings; Windows Desktop Runtime is unavailable. Crapper, Dryer and Mutator were not available. No CRAP, duplication or mutation metrics were obtained. A standalone Linux test demonstrated a blocked waiter before the disposal change and cancellation afterwards, including 1,000 concurrent registry registration/stop races. The Windows ACL implementation and Shell integration have not been executed. On Linux, the targeted SFTP suite reported 38 passed and one skipped; the full suite reported 568 passed, two failures because cmd.exe is unavailable, and one skipped. A local OpenSSH attempt reached the daemon but failed at pre-authentication because chroot is not permitted. No Windows Explorer environment was available.

Before treating D4 as complete: design and test restricted staging and crash recovery; resolve or explicitly prevent unsafe use where no-follow guarantees cannot be obtained; implement bounded cancellation and correct ownership without breaking COM clients; run adversarial SFTP tests and Windows Explorer end-to-end tests for every scenario above, verify hashes and partial results, measure repeated-drag memory, and run D1–D3 plus upload regression with PR #3 applied separately. Capture red/green evidence for behavior fixes. Evaluate all findings rather than assuming CI proves safety.
