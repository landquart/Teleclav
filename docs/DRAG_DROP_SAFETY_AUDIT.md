# D4: reverse drag-and-drop safety audit (incomplete)

Audit date: 2026-10-30. Base: D3 `d8358e6c044901ae2977f3790152406f0043e886` (draft PR #6). This is a static, partial audit, not a release certification. D4 includes partial staging and cancellation changes; the remaining requirements below are not complete and the Windows changes are not verified on Windows. D1-D3 themselves remain unverified with Explorer and a real SFTP server. Do not merge on the strength of this document.

## Findings and residual risks

1. **TOCTOU / untrusted server:** `EnsureDirectoryComponents` and `GuardedSftpDownload` perform separate path checks and `OpenRead`. Replacement between checks and open, including a temporary symlink restored before subsequent checks, can escape the selected tree or select different content. Matching attributes and FSTAT size do not establish identity or immutable contents. Public SSH.NET API as investigated in D3 does not provide an atomic no-follow open of each path component or a verified full handle identity. Treat remote hosts and concurrently writable trees as untrusted for this guarantee; no safe guarantee is claimed. D3's checks reduce detectable cases, not the race. Server-side isolation or a protocol/implementation with suitable handle-relative no-follow semantics must be evaluated before claiming a fix.
2. **Sensitive staging:** `ShellStagingDirectory` now uses an exclusive Win32 directory creation with an explicit protected ACL and rejects volumes without persistent ACL support. This has been cross-compiled but not run or verified on Windows; access by administrators, SYSTEM, the same user, or parties with suitable parent-directory rights is not excluded. Parent-path/reparse substitution is not completely addressed. Cleanup is best effort. Crash, failure to delete, or retained COM references may leave sensitive data. No stale cleanup exists. A safe cleanup design must avoid deleting active sessions and defend against reparse-point substitution; blindly deleting old directories is unsafe. An inheritable deny-execute ACL for the current user was added but is not verified on Windows and does not prevent an administrator or owner who changes the ACL from executing files. These remain unresolved security requirements.
3. **Cancellation / liveness:** `GetData` passes `CancellationToken.None` to the cache and synchronously waits. Cache disposal now also unblocks waiters independently of whether the download cooperates. The view requests cancellation of tracked transfers on tab disposal or SFTP disconnection. Cleanup still waits for `EndOperation` when async extraction has begun. If a consumer fails to end the operation, the retained COM reference and cache may survive indefinitely. Cache waiters now have an absolute 24-hour per-file limit; timeout cancels the cache but does not forcibly terminate a synchronous SFTP read or guarantee a bounded COM lifetime. A stalled synchronous read observes cancellation only around calls; the configured SFTP exchange timeout is 15 minutes, not a bound on the whole operation. Explorer cancel, Escape, tab/app close, and forced disconnect are not proven to stop every operation. A timeout must not free an object while a consumer still owns it.
4. **Final destination and partial batches:** the temporary-file commit applies only to Teleclav's staging, not the destination written by Explorer. Explorer may create or overwrite files, leave partial files, or complete part of a tree. This code cannot certify an atomic batch or independently confirm that every destination file is durable and correct. Failure of an item must not be interpreted as full success; actual Explorer behavior and reporting are untested.
5. **Privacy:** `LoggingRemoteBrowser.DownloadFileWithinLimitAsync` records remote and local paths, sizes and operation status when session logging is enabled. Paths may themselves be sensitive. The inspected transfer method does not log contents or credentials, but this is not a complete privacy or telemetry audit. Shell drag UI now maps exceptions to fixed localized messages and its COM boundary returns a fixed error string, but other application paths and log failures have not been fully audited. Rollback logs the temporary path and exception.
6. **Lifetime and memory:** lease cleanup is synchronized and idempotent in the examined paths, but finalizer timing is nondeterministic; `ShellReadStream` now serializes disposal and local reads/seeks; it releases the lock before invoking a destination COM stream. Whether concurrent COM calls or disposal cause races is unverified. No real repeated-drag stress or process memory measurement was run.
7. **Change during read:** different size/visible attributes are rejected when observed. Same-size changes with preserved or restored timestamps, and changes after a check, may pass; there is no snapshot or verified source hash. A successful staged read is not proof of the originally planned state.

## F3: staging cleanup and crash recovery (incomplete)

F3 is based on F2 head `56038c77411512dbbf653f683bd82a85ef50f556`. Statements above describing pre-F2 `GetData` and lifetime behavior are historical; see [SHELL_ASYNC_LIFETIME.md](SHELL_ASYNC_LIFETIME.md) for the current design. The ownership and path-security gaps below remain release blockers.

`ShellStagingDirectory` creates an ACL-protected directory under the process TEMP path. `ShellDownloadCache` owns the staging directory and schedules the SFTP download. `DownloadFileWithinLimitAsync` owns an exclusive `.part` file until it either moves it to the numbered cache path or attempts rollback. Each opened cache reader has a lease; the cache currently waits for downloads and readers before its cleanup attempt. A COM wrapper or finalizer can delay lease release. If the process terminates, in-memory ownership is lost and a staging directory can remain on disk.

The existing Windows ACL test actually passed in [F2 CI](https://github.com/landquart/Teleclav/actions/runs/41484767160): it checked a protected DACL, allowed identities and the inherited execute-deny ACE on a file. This is an ACL structure check on that runner; it does not prove safety against a process with the same identity, an administrator, SYSTEM or a principal with sufficient access to a parent directory.

The cache formerly swallowed `IOException` and `UnauthorizedAccessException` during `Directory.Delete`. F3 exposes the failure to the cache owner and records a warning without the path, source name, file content or credentials. A Windows test holds a cached file without delete sharing and checks the failure. This is diagnosis, not guaranteed cleanup: after a failure the object has no safe automatic retry or durable recovery record. The inherited path-based recursive delete still lacks a race-free proof of directory identity and ancestor stability. A privileged or same-user adversary, or an actor able to replace a parent, may exploit path substitution. This issue is **not fixed**, and the current cleanup must not be described as safe against substitution.

No startup scavenger is enabled. A name prefix, age, PID, marker file or a path checked before deletion does not by itself prove ownership or exclude active instances and reparse-point substitution. A production recovery mechanism needs a protected ownership record tied to volume and file identity, a live-instance exclusion mechanism, and deletion through verified handles while refusing reparse points; it needs Windows tests for crashes, concurrent instances and parent and child substitution. Automatic deletion is deliberately not introduced until those requirements can be demonstrated. Files held by Explorer must remain available, and ordinary deletion does not guarantee physical erasure from SSDs.

**Unverified / incomplete:** handle-based ancestor and child identity, safe retries after sharing violations, bounded recovery at next startup, two-process ownership, crash recovery, junction and symlink attacks, disk-full and failed-publish cleanup, and long-lived locked files. A failed or abandoned transfer may leave confidential data in TEMP. The user-facing warning does not identify a path, and no complete secure-erasure mechanism is claimed. Existing `AtomicLocalFile.Rollback` can log a temporary path; the transfer audit must not claim that paths are absent from all application logs. Do not merge this draft as complete F3.

### F3 continuation: handle-bound cleanup (still incomplete)

The preceding F3 notes about recursive deletion describe the baseline, not the new Windows path. The cache now opens and retains handles to the staging directory and its ancestors without delete sharing, rejects reparse-point directories, records each completed file's volume and file index, and verifies that identity on an open no-follow handle before marking the file for deletion through that handle. Unknown entries and changed identities cause cleanup to fail closed. Deletion is retried three times after short delays while the handles remain held; the error is logged without the pathname. Active cache readers and downloads still postpone cleanup.

The production cache now pins the ancestors first, then creates the staging directory with `NtCreateFile` relative to the pinned parent and retains the handle returned by the same exclusive creation operation. A deterministic Windows regression test exercises substitution at the former creation-to-open boundary. This does not establish an end-to-end guarantee for arbitrary hostile parents: ancestor components are opened in sequence and their access rights and initial identities are not fully authenticated. A file that fails before its identity is registered can be left behind rather than deleted. Temporary data can remain after the bounded retry period or process crash. There is still no startup recovery, protected ownership journal or verified exclusion between a stale instance and a live one. Do not treat this draft as complete F3. Same-user processes, administrators and SYSTEM are not excluded by the staging ACL.

A Windows test first demonstrated that the baseline deleted a file in a substituted staging directory. In the later Shell probe, directory and registered-file substitution tests passed, as did the existing ACL and transfer tests. These tests do not establish atomic staging creation, crash recovery, junction handling, Explorer behavior or disk-full recovery. Consult the PR for exact run and commit identifiers.

The Windows Shell probe also exercised 200 successive cache transfers with no remaining staging directories, handle growth within 64 handles, and managed-memory growth within 16 MiB. These are test thresholds for this short run, not exact retained measurements or a guarantee for indefinitely running sessions. The production handle-created directory's protected ACL and inherited deny-execute entry were tested on the hosted Windows runner. Full interactive Explorer, crash recovery, and the remaining adversarial and disk-full cases are not established by these checks.

A further Windows regression test held a staged file locked beyond the original 2.2-second retry window. The baseline left the directory behind after unlock; extending the bounded retry schedule to approximately 30 seconds made the same test pass. The retry is still finite, and a longer lock or a crash can still leave temporary data. This does not implement crash recovery.

A Windows regression test demonstrated that a recorded cached file could be replaced before a repeated open and the replacement would be read. The cache now compares the identity obtained from the opened file handle with the identity recorded for that entry, and closes the handle on mismatch. The test and all 17 cache tests passed on Windows after the change. The initial registration happens only after download, so this does not close the preceding registration gap or implement recovery after a crash.

### F3.1: persistent ownership foundation (2026-11-03)

This section supersedes the earlier F3 statements about TEMP, unauthenticated ancestor permissions and absent ownership metadata. F3 as a whole is still incomplete; startup discovery/recovery is F3.4. Interactive Explorer validation is not claimed by this change.

Production staging is now `%LOCALAPPDATA%\Teleclav\Staging\<random Guid N>`. The known-folder path must be fully qualified, on a fixed local NTFS volume. UNC/device paths, network/removable volumes, non-NTFS filesystems, missing profile ancestors and any reparse-point component fail closed. Ambiguous Win32 components (device names and trailing dots/spaces) are rejected before path normalization so relative native opens and path-based SFTP/cache access cannot resolve different objects. There is no TEMP fallback. This deliberately respects a relocated LocalAppData known folder when its properties pass validation, but does not follow TEMP/TMP: a custom TEMP is not a source of staging trust or capacity. Portable builds use the same per-user location and need no administrator privileges; they intentionally leave application staging state in the profile. The Teleclav namespace does not use Heimdall's directories. Multiple installations under the same account share the root, but every drag gets a cryptographically random GUID operation name and its own exclusive ownership lease.

The audited ownership chain is:

| Code | Owned resource / handoff |
| --- | --- |
| `ShellVirtualFileDrag` | Owns cache and F2 lifetime; releases its retained COM async reference during cleanup. Native `STGMEDIUM` ownership passes to the receiver under COM rules. |
| `ShellAsyncLifetime` | Counts callbacks, streams and async extraction; calls cleanup only at the existing F2 boundary, or cancellation/expiry. Owns its idle timer. |
| `ShellTransferRegistry` | Holds cancellation delegates until completion/session stop; owns no staging files. |
| `ShellDownloadCache` | Owns guard, cancellation source, download entries and space accounting. Keeps the operation until all downloads and reader leases finish; bounded cleanup retries retain the guard. |
| `ShellStagingGuard` / journal | Own directory/ancestor handles and journal stream; durable records identify only files registered by the cache. `Dispose` releases ownership handles without recursively deleting data; `Delete` validates known entries before handle-based deletion. |
| `SftpBrowser.DownloadFileWithinLimitAsync` | Owns the client-lock lease and exclusive `.part` FileStream; the stream is closed before non-overwriting publication. Uses ordinary SFTP read operations. |
| `AtomicLocalFile` | Selects a unique sibling partial name, publishes by move and attempts rollback; retains no handles or durable ownership after returning. |
| `ShellDeferredStream` / `ShellReadStream` | Own the cache reader lease and its FileStream until release/finalization. Current drag uses the stream-only COM wrapper. The legacy public `(FileStream, directory)` wrapper is not used by current drag and is not a recovery API. |

The initial drive-root open is a trust boundary, not an already-authenticated arbitrary parent path. Windows' local drive namespace and trusted account/OS administrators are assumed trustworthy. From that handle onwards, components are opened one at a time with `NtCreateFile` relative to the retained parent, with no delete sharing and `FILE_OPEN_REPARSE_POINT`. Before traversing further, code checks the actual handle's directory type, absence of reparse attributes, owner and DACL. Ancestor owners are restricted to the user, Administrators, SYSTEM or TrustedInstaller. Non-inherit-only grants allowing other principals to delete/change existing ancestors, their ACL/owner, attributes, EAs or reparse data are refused. `FILE_ADD_FILE` aliases `FILE_WRITE_DATA` (one of the rights accepted for [setting reparse data](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-fsa/4aeefef8-92c3-4abc-af7a-a610caf8a165)) and is also refused for untrusted principals; only grants to create sibling directories (`FILE_ADD_SUBDIRECTORY`) on shared ancestors are permitted. Unsupported ACE forms fail closed. This rejects some legitimate custom profile ACLs rather than trying to repair them. Held handles prevent rename/deletion while in use; holding a handle alone does not authenticate the initial namespace or protect against same-account ACL changes.

Only the application parent and staging root may be created. `FILE_OPEN_IF` creates or opens each component relative to its already-verified parent; a pre-existing object is verified and never chmodded/repaired or cleared. These private directories and each operation must have the current user as owner and exactly the protected application DACL: current user, Administrators and SYSTEM full control, plus the pre-existing inheritable deny-execute rule for user-owned files. A mismatch, unexpected identity, reparse point or insufficient access stops the operation. The final operation uses `FILE_CREATE`, with its ACL installed atomically; its returned handle is retained. Calls putting a raw parent handle into `OBJECT_ATTRIBUTES` hold a `DangerousAddRef` until the native call returns. Failed native output handles are disposed. Directory and ancestor SafeHandles belong to the guard; the journal SafeHandle belongs to its FileStream. Borrowed reader SafeHandles are only inspected, never closed by the guard.

Before the cache exposes its path or starts a download, `.teleclav-owner` is created exclusively relative to the operation directory and flushed to disk. It is opened without sharing, so another process following the ownership protocol cannot claim the live operation. Journal opening also validates the actual regular-file type, current-user owner and exact protected file DACL (including deny-execute), through that same handle. Version 1 records contain a format marker/version, initial active state, the random operation ID, 64-bit volume serial and 128-bit file ID (`FILE_ID_INFO`) of both root and operation, and their attributes. Completed-file records persist the numeric cache name and the same file identity; `Record` flushes the record before adding it to the in-memory dictionary or serving a reader. A final transition records cleanup-pending before deletion. There is no PID, clock-based ownership claim, credential, content or remote path.

Records are length-bounded, hash-chained SHA-256 frames (journal size capped at 16 MiB), not arbitrary object deserialization. Checksums detect accidental corruption and torn writes; they are **not authentication against deliberate tampering**. The source of trust is the verified ACL and object chain. `Reopen` acquires the exclusive journal handle, verifies its header against the handles for the current root and operation and the directory's random name, then validates every frame, entry name, duplicate and state transition before returning the restored identity dictionary. It does not enumerate stale operations, invoke startup recovery or delete anything. A missing, truncated, damaged or transplanted journal fails closed. An orphan from failure before a durable header is not adopted automatically. Frame-boundary truncation can leave a valid earlier prefix; entries absent from that prefix remain unknown and are not deleted.

Cache quota (16 GiB), independent reader leases, COM IStream and F1/F2 lifetime rules are retained. A check of currently available bytes on the pinned staging volume refuses obviously insufficient space before each new download; it is not an allocation reservation, and concurrent writes/disk exhaustion can still fail later. SFTP download still creates its exclusive sibling `.part`, writes through the bounded stream, closes it, and publishes without overwrite. The operation owns the private directory before any of these writes. The SFTP implementation owns the partial handle and rollback; `AtomicLocalFile` does not retain an identity after returning. The cache owns the completed file record; the reader owns its FileStream and releases the cache lease on disposal. The transfer registry cancels; it does not own filesystem handles. No SSH exec, Python or non-SFTP download dependency is introduced.

| Threat | Actual guarantee / boundary |
| --- | --- |
| Ordinary filesystem failures and insufficient permissions/space | Creation, journal writes and validation fail visibly; unrecognized entries are preserved. No secure erasure guarantee. |
| Process crash | Flushed ownership/file records survive an ordinary process crash; Windows releases the exclusive lease. Reopening is implemented. Startup scanning, cleanup policy and crash-injection acceptance remain F3.4. Hardware/power-loss durability beyond the filesystem's flush guarantees is not claimed. |
| Another unprivileged Windows account | Validated private ACL prevents reading/modifying operation contents. Checked ancestor permissions and relative opens prevent that account from substituting existing components under the assumed trusted local namespace. |
| Another process under the same account | Cooperative processes are excluded by the live journal lease. A hostile same-account owner can change ACLs or forge records; no complete protection is claimed. |
| Administrator / SYSTEM | Trusted and outside the adversarial security boundary. Can bypass/change ACLs and impersonate the user. |
| Journal corruption | Bounds, header identity, hash chain, entry validation and state transitions refuse damaged/transplanted records. Invalid/unknown data is never authority to delete other entries. |

F3.4 can build on `Reopen` and the durable identity records. It must add bounded startup discovery and scheduling, crash tests, policy for incomplete operations, and allocation/publication records for `.part` files. Unknown files, failed atomic rollback, or a crash between file publication and its durable registration currently leave data in the private operation rather than authorizing deletion. Extending the record protocol for partial files does not require replacing the root, directory identity, ACL validation or lease architecture. Existing remote-source TOCTOU limitations and existing rollback-path logging elsewhere in this audit are unchanged.

The Windows CI now runs the staging/cache regressions as a required early step after the Debug build, with a separate `staging-ownership.trx` uploaded alongside the full test results. The original regression test was committed before implementation (`2840e2d8d0b197c7530ff0587d2499de4a18f53e`, [Windows CI](https://github.com/landquart/Teleclav/actions/runs/41597568343)); it asserts both the persistent root and an ownership journal before downloading. Exact implementation SHA and Windows CI outcomes are maintained in the description and checks of [PR #12](https://github.com/landquart/Teleclav/pull/12). Local source-linked compilation of the staging/cache classes and regression tests succeeded without warnings; Linux execution is not evidence for Windows ACL, sharing or NT API behavior.


### F3.2: creation-to-deletion ownership protocol (2026-11-03)

This section supersedes F3.1's statements that partial files and the publication-to-Record window remain unowned. Startup discovery/scheduling remains F3.4. The Shell cache no longer calls `Record` after a path-based SFTP download. Its callback receives a bounded, write-only, non-owning view of an already-created file. `SftpBrowser.DownloadToStreamWithinLimitAsync` performs ordinary guarded SFTP reads into that stream, never opens a local path, never closes the destination, and never publishes or rolls it back. The ordinary path-based API remains available and reuses the same bounded copy. `AtomicLocalFile` continues to serve ordinary downloads; it no longer allocates Shell staging partials. F1/F2, cancellation, cache quota, independent reader streams and per-index download deduplication remain in place.

Each file has a random object GUID and a generated relative name `<numeric-cache-index>.<object-guid>.part`. The operation GUID is already bound to the root/directory identities in the journal header. Version 2 adds bounded file-state snapshots with target index, object GUID, expected size, regular-file kind (in the creation tag), state, partial/final location and, once known, volume/file ID. States are `Reserved -> Created -> Writing -> Written -> Publishing -> Published -> Deleting -> Deleted`; cleanup may move an incomplete state directly to Deleting. Every snapshot is flushed with `FileStream.Flush(true)` before the next dependent filesystem operation. Replayed records must follow legal transitions, preserve IDs/size, obey name bounds and remain on the operation volume. Version 1 journals are accepted for conservative cleanup of their recorded final files; they cannot create version 2 files and unknown legacy partials are never adopted.

The critical creation sequence is:

1. Flush Reserved, containing the object ID and predetermined partial/target names, before creating the file.
2. Issue one directory-relative `NtCreateFile(FILE_CREATE)` request with the exact protected file DACL and an EA named `TELECLAV.OWNER`. The EA value contains its own format version, regular-file kind, operation GUID and object GUID. Existing names cause failure; no existing object is opened for writing or retagged. FILE_WRITE_THROUGH is requested. Unsupported EA/filesystem/filter behavior fails closed, without a path-based fallback.
3. Keep the returned exclusive handle. Validate regular-file type, no reparse point, exactly one hard link, volume, ACL and the exact EA read by `NtQueryEaFile`. Flush Created with the actual FILE_ID_INFO before allowing any downloaded bytes. The same handle backs all writing and publication.
4. Bound writes to the declared size, verify the actual final length, Flush(true), and flush Written. Flush Publishing before a handle-based directory-relative `NtSetInformationFile(FileRenameInformation)` with replacement disabled. Flush the data handle again and recheck identity before flushing Published. Readers are served only for a durable Published record and matching opened file ID.
5. Before deleting, validate **all** visible entries through no-reparse, exclusive relative handles. Then flush Deleting before marking those handles for deletion; close them before flushing Deleted. A missing file is reconciled idempotently. Unknown entries, wrong tags, ACLs, types, multiple links or changed IDs refuse the whole preflight without deleting other entries.

Crash after file creation but before Created is now represented by a durable Reserved record **and** the creation-time EA on the file. Reopening can verify that specific tag/ACL/type through the real object handle before recording its identity for cleanup. Intent/name alone is never deletion authority. A foreign colliding file without the tag is preserved, even when its name is exactly the reserved name. In Publishing, either the tagged partial or tagged final name is accepted for cleanup; two candidates or a foreign final target fail closed. A final filename without a Published record is not reported as completed. The recovery method performs safe abandonment/cleanup, not automatic resumption of an interrupted remote transfer.

The threat boundary is unchanged: the validated private operation ACL excludes other unprivileged accounts, the exclusive operation journal excludes cooperative processes, and cryptographically random IDs bind the intended creation. A hostile process under the same Windows account could forge/copy EAs and journals or change ACLs, and administrator/SYSTEM can bypass access controls; these actors remain outside the claimed guarantee. EAs and hash checksums are not cryptographic authentication against the account owner. Creation-time metadata is supplied in the native create request rather than by a separate later file write. If the filesystem returns an ambiguous failure or the matching tag cannot be proved, data is preserved for inspection, never inferred to be ours from a name.

For an ordinary process termination, completed native operations remain in the mounted filesystem and the OS closes the process's handles. A bounded incomplete last journal frame after a valid header is truncated back to its verified prefix and flushed before further records are appended. No downloaded bytes can precede a fully flushed creation intent, so the creation tag bridges the case where the next identity frame was torn. An invalid header, unsupported version, invalid complete frame/checksum, inconsistent transition or oversized journal fails closed. Complete-frame truncation can retain a valid earlier prefix; the resulting state must still pass tag/ID/location validation. No invalid prefix authorizes deletion.

`Flush(true)` requests flushing through the Windows file API; handle-based same-volume rename provides namespace publication with no overwrite. These are not a transactional commit across the journal, file, directory and storage controller. An OS crash, power loss, failing hardware or a filter that violates filesystem semantics can lose namespace/data changes despite a flush. No absolute hardware durability, secure erasure, or atomic multi-file cleanup is claimed. Missing or inconsistent durable state fails closed. ### F3.3: deletion identity, pinned enumeration and retry safety (2026-11-03)

The F3.3 audit found three observable defects: calling Guard.Delete while its writer was active irreversibly changed the journal to cleanup-pending; an operation ACL modified after opening was not checked at deletion; and calling Delete again after success raised ObjectDisposedException instead of leaving a reused path untouched. These were reproduced on `e5eb018515c6026a3918e8c82771b0f938fd990a` ([Windows run 62](https://github.com/landquart/Teleclav/actions/runs/41678735974)): 78 passed, three new regressions failed, zero skipped. The failures were respectively `Staging operation cannot create files`, missing expected refusal, and ObjectDisposedException. No production fix preceded that red run.

The Guard now counts active writers under its gate. Delete refuses them **before** setting cleanup state; Dispose defers closing the journal, directory and ancestors until the writer's retained file handle is closed. This is additional protection below the existing cache reader/download counters and COM lifetime. The exclusive journal lease remains held throughout a live write. Successful teardown is remembered, so repeating Delete performs no filesystem resolution and cannot touch a new object at the old path.

Before cleanup, all retained parent handles are rechecked for directory type/no reparse and trusted ACL; private root/operation ACLs and captured root/operation identities must still match. The exclusive journal handle is checked for type, volume/file ID, single link, ACL, expected length and complete hash chain against the last committed in-memory digest. This also detects corruption/truncation of a live journal; Reopen still validates the persisted protocol independently. A journal hard link is refused both initially and on revalidation. Checksums remain corruption detection, not authentication against a hostile account owner.

Enumeration is now `NtQueryDirectoryFile(FileNamesInformation)` against the operation handle, with a synchronous single-entry bounded buffer, checked byte counts/UTF-16 lengths and duplicate/entry-count limits. Cleanup performs no string-path enumeration and no absolute child reopens, including the legacy v1 branch. Every candidate is opened with native relative FILE_OPEN, FILE_OPEN_REPARSE_POINT and FILE_NON_DIRECTORY_FILE, DELETE/READ_ATTRIBUTES/READ_CONTROL/READ_EA/SYNCHRONIZE, and share mode zero. Names only select candidates from the persisted journal; they are never ownership authority. All visible entries are preflighted before deleting any file. V2 requires matching creation tag, regular type, no reparse, one link, same volume and recorded identity where available; legacy v1 requires its recorded identity, regular type, same volume, one link and trusted permissions. Legacy unknown partials remain refused.

After all validation, Deleting records are flushed. Each exact verified handle is checked again immediately before disposition, marked for deletion, closed, then recorded Deleted. No child is reopened between its last identity check and deletion. A process exit between the first file's close and its Deleted record leaves a replayable Deleting record; a missing file is reconciled, while a new object at the same name must pass the original identity/tag checks and is otherwise preserved. Other held candidates are closed without disposition if the loop fails. Failures are not reported as completed cleanup.

Before removing the journal, the pinned chain/journal are revalidated and the directory is enumerated again; unexpected late entries preserve the journal and are refused. Final directory disposition is attempted only on the retained, still-verified empty directory. A failure after journal unlink can be retried in the same process only through the pinned identity, with no unknown children. A process crash in the final journal-unlink/empty-directory-close interval can leave an empty unjournalled directory: it is not authority to delete data and must be quarantined/handled conservatively by F3.4. No cross-file/directory atomic transaction is claimed.

The cache's existing seven retry delays (200, 500, 1500, 3000, 5000, 10000, 10000 ms) remain bounded. Cleanup retries never force-close reader/writer handles. An internal completion task lets a test await actual exhaustion instead of guessing a timer interval. Exhaustion retains the file, journal, pinned owner and observable CleanupFailure; later explicit retry can succeed after unlocking. Process shutdown releases the lease, allowing the persisted protocol to be reopened after restart. Automatic startup scheduling is still F3.4.

## F3.4: bounded startup discovery and safe abandonment

This section supersedes earlier statements that startup discovery is absent. After the normal single-instance decision, product startup schedules recovery off the dispatcher. Independent settings profiles still share per-user Shell staging; only the exclusive ownership-journal lease authorizes abandonment of an operation. Privilege-helper and suppressed test lifecycles do not run product recovery. Application exit cancels future recovery work without waiting on or force-closing another owner's streams.

Discovery opens only an existing root. It never creates missing application directories, repairs permissions, follows a root/operation reparse point or recursively removes an unrecognized tree. The same fixed-NTFS, protected-ACL and ancestor-handle checks used by creation apply. Root enumeration uses `NtQueryDirectoryFile` against its pinned handle. A bounded name snapshot is taken before deleting anything, avoiding mutation of our own enumeration cursor. The root/ancestor handles remain pinned without delete sharing throughout the pass. Each candidate is reopened through the verified component chain, its root identity is compared with the discovery owner, and the exclusive journal/header/operation identity is validated before the F3.3 deletion protocol runs. A GUID-shaped name is only a candidate, never proof of ownership. No age/PID inference is used.

The startup policy has at most three passes, two seconds between passes, at most 128 processed root entries (129 enumerated to detect truncation), and a five-second cooperative cancellation budget per pass. Journal replay remains bounded by its existing 16 MiB limit. Cancellation checks were added to native enumeration, preflight and per-object deletion; an interruption retains a replayable journal. Synchronous filesystem/driver calls and journal flushes cannot be forcibly interrupted by this budget, so it is not a hard wall-clock guarantee. No recovery task is awaited by the UI or application exit. A pass stopped by its budget reports incomplete work, not completed cleanup.

Locked, live, corrupt, substituted, unknown and unjournalled objects remain in place. Their journal/identity checks are reused rather than weakening ownership to make a scan succeed. A later pass/start can retry after a reader or active process releases its handles. Retained objects or limits produce count-only diagnostic warnings without paths/content. Persistent refusals are not retried indefinitely. More than 128 persistently unrecognized early entries can prevent later candidates from being visited during the bounded passes; the warning remains, and no eventual-drain guarantee is claimed for an unbounded or adversarial root.

An empty unjournalled directory left after final journal unlink is intentionally retained, just like an unknown nonempty directory. F3.4 does not invent deletion authority from emptiness, a GUID or a timestamp. This can leave empty metadata residue and conservatively retained data after corruption. Recovery safely abandons interrupted transfers; it does not resume remote downloads or report them as completed. The F3.1-F3.3 threat boundary, hardware/power-loss limits and interactive Explorer acceptance limits remain unchanged.
